    Using Pigeon

    Talk to it like a colleague. A small set of phrases is answered from what Codex has already done. Everything else is passed to your original session.

    Ask what it is doing#

    Recognised phrases include what are you doing, how's it going, status, are you stuck, how are the tests going, and what's failing (also in Spanish and Turkish). Pigeon reads the latest turn and replies. No model turn is created and nothing is interrupted.

    Counts and failing test names appear only when they exist in observed test output. Otherwise Pigeon passes your question to Codex rather than invent an answer.

    Give an instruction#

    Anything not recognised as a special phrase is an instruction, for example Focus on latency first. If a turn is active, Pigeon steers it with turn/steer, guarded by that turn's ID. If the session is idle, it starts the next turn in the same session. Pigeon confirms (“Passed that to Codex on …”) only after Codex accepts the input.

    This includes free-form questions such as “why did you pick that library?”. They are delivered to the working session as input; there is no separate side conversation. See routing.

    Pause#

    Pause, stop or interrupt asks Codex to interrupt the exact active turn. It is not a checkpoint: a terminated command is not restored. If Codex is disconnected, the stop is rejected, never queued for later.

    Continue#

    Continue is simply a new instruction in the same session.

    Ask to be told when it finishes#

    Let me know when it's finished watches the exact current turn. If Codex is already idle, Pigeon says so and suggests asking for the latest result.

    Approve a request#

    When Codex asks to run a command, Pigeon posts the project directory, the complete command and the reason, with Approve once and Deny buttons. Typing “yes” does nothing: only the button counts. Controls expire after 10 minutes, and are invalidated by reconnects or by a local decision. Codex still applies its own policy.

    File-change approvals, broad permission bundles, truncated commands, and unknown request types stay in Codex, and Pigeon tells you to look there.

    Answer a question from the agent#

    When Codex asks one non-secret question (Plan mode), reply in the thread to resolve that exact request. Secret fields and multi-question forms stay local. When the agent calls pigeon_ask_human or pigeon_request_human_action, your reply goes back to the waiting call.

    Example: an Authenticator prompt
    Pigeon  Quick one — Microsoft is asking for number 88. Can you approve that?
You     Done.
Pigeon  Passed that back to Codex on agentlane.

    Approve in Microsoft's own app. Pigeon never touches Authenticator, and the agent is told to verify that sign-in really succeeded.

    What gets a notification#

    proactivenessYou get
    quietHuman requests, failures and interruptions, and anything you explicitly asked for.
    important (default)The above plus completed turns.
    updatesAlso progress, at most once a minute per session.

    Change the voice#

    terminal
    $ node dist/cli.js voice
$ node dist/cli.js voice set humour off
$ node dist/cli.js voice set proactiveness quiet
$ node dist/cli.js voice set language tr      # en, es or tr
$ node dist/cli.js voice reset

    Options: formality (casual, neutral, formal), humour (dry, off), verbosity (brief, normal, detailed), proactiveness, language, address. The running service picks changes up within five seconds.

    Several projects#

    Each Slack thread is bound to one exact Codex session. Send sessions, choose, and keep talking in that thread. A stale binding fails closed: Pigeon tells you the session went offline and sends nothing. It never falls through to another project.
