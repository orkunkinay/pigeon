desc: The real routing rules: deterministic intents, observed-state answers, steering, and native approvals. ---

Pigeon's rule is that a casual question should not disturb working code, and an approval should never be a guess. Here is how that is actually implemented today.

No conversational fork yet. An earlier design idea was to answer questions in a forked copy of the session. That is not in this codebase. The sections below describe what exists. {{pill:no}}

Why status is answered locally

Asking “what are you doing?” while Codex is mid-task is the most common message. Reading state creates no turn and no user item, which was verified with a real Slack message (the in-progress turn ID was unchanged). The phrase list is deliberately small and deterministic, so Pigeon never claims to understand more than it does.

What this means for free-form questions

“What's the bottleneck?” is not a recognised phrase, so it is an instruction and reaches the working session. If Codex is mid-turn it enters as steering input. It is better to treat Pigeon as a way to talk to the one agent, not as a separate assistant that is aware of the work.

Fail-closed routing

  • A thread with an existing binding uses that session or fails. A stale binding never falls through.
  • With no binding, exactly one live session is selected automatically. Several produce a selector. Pigeon does not guess.
  • Selecting a session does not send the message that prompted the selector.
  • If delivery cannot be confirmed (for example Pigeon crashed mid-send), the instruction is marked uncertain and is never replayed. Pigeon tells you to check Codex first.
  • Queued instructions expire after five minutes.
