How Pigeon finds Codex

Pigeon does not launch Codex and does not scrape a terminal. It connects to the shared Codex app-server daemon over the local control socket under CODEX_HOME (default ~/.codex), using a WebSocket over a Unix socket. Nothing listens on a TCP port.

  • It lists threads that are loaded in that daemon (thread/loaded/list). Internal subagent threads and threads that are no longer loaded are left out.
  • When you press Connect, it joins that thread with thread/resume on the same server, without overriding model, directory, or permissions.
  • If the control socket is unavailable it may run Codex's own idempotent app-server daemon start, at most once per 30 seconds. It never upgrades, restarts, stops, or enables remote control on Codex.
{{sh:terminal}} $ codex app-server daemon version # should report a reachable daemon $ node dist/cli.js sessions # JSON list of live, controllable sessions {{/sh}}

An older Codex client can fall back to a private embedded runtime even while a daemon exists. doctor tells you whether Pigeon can see a shared runtime, not whether a given window is attached to it. If a window is missing from sessions, that is the first thing to suspect.

MCP tools and the skill

setup (and install-agent) gives the agent a way to reach you on its own initiative. All of it is reversible and tracked by a receipt in Pigeon's home directory.

WhatWhere
MCP server pigeonRegistered with codex mcp add. A locally owned launcher runs pigeon mcp from Pigeon's immutable installed runtime.
Skill~/.agents/skills/pigeon/SKILL.md
Awareness blockA <!-- pigeon:begin --> … <!-- pigeon:end --> section in AGENTS.md (or AGENTS.override.md if that exists) under CODEX_HOME.

If a pigeon skill or MCP entry already exists that Pigeon did not create, or you edited the block, setup refuses and preserves it rather than overwriting. New Codex sessions load the awareness; existing ones may need a restart to see the skill.

The four tools

ToolUse
pigeon_get_statusRead-only: is Slack connected and paired, and what voice preferences apply.
pigeon_notify_humanQueue a short update without blocking. “Queued” is not “delivered”.
pigeon_ask_humanAsk a question and wait for the correlated reply. Pending requests survive; reuse request_id.
pigeon_request_human_actionAsk for an outside action, such as approving a Microsoft Authenticator number. The reply is a human report, not proof; the agent must verify.

Codex's own tool consent still applies. The first use of a sending tool may need local approval, and a non-interactive session with approval policy never can reject a send. Pigeon reports the rejection instead of claiming delivery. Authorize the communication tools in Codex before you walk away.

The tools also work from private Codex runtimes such as codex exec: the answer returns to that process's waiting call. Independent Slack steering and native approval forwarding still require a session loaded in the shared daemon.

These tools cannot grant permissions, replace approval buttons, or collect passwords, OTPs, recovery codes, or tokens. Each call is tied to the Codex thread ID that Codex supplies, never inferred from the working directory.

{{sh:terminal}} $ node dist/cli.js doctor # reports skill discovery and MCP tool verification $ node dist/cli.js install-agent # repair or re-install skill + MCP {{/sh}}

Limits to know

  • Pigeon lists live sessions only. A conversation saved on disk is not a live connection. See Sessions and recovery.
  • There is no atomic “join only if already loaded” call in the public protocol. In a narrow race a thread can unload between the check and the join; Codex may then cold-resume it. A successful join of a continuously loaded thread was demonstrated; a universal guarantee is not claimed.
  • After a Codex daemon restart, Pigeon reconnects only to loaded identities and invalidates old approval controls. This is experimental.
